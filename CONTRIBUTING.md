# Contributing to Innsegl

Two rules decide whether a pull request can be merged at all. They are not
open for relitigation in review, so they are stated first.

## 1. Test-driven development is a merge gate, not a preference

**No production code exists without a test that was observed failing first,
for the expected reason.**

1. Write the failing test that specifies the behaviour. Run it. Confirm it
   fails **for the expected reason** — a test that fails on an import error
   or a typo is not red, it is broken.
2. Write the minimum code to pass.
3. Refactor with the tests staying green.
4. Commit only in a green state, and say in the commit message which test
   drove the change.

What follows from that:

- Every bug fix starts with a regression test that reproduces the bug.
- Every failure mode gets a dedicated failure-injection test before its
  handling code is written. Failure handling written without a
  failure-injection test is untested code and will be rejected.
- Integration tests for the signing and anchoring paths run against real
  containerised SPIRE and a local Fulcio/Rekor — never mocks. A mocked
  Fulcio proves nothing about independent verifiability. Mocks are fine for
  unit and contract tests.
- Coverage is a floor, not a goal: **90% line** coverage on the MCP server
  and ledger packages, and **100% branch** coverage on hash-chain append,
  segment sealing, signature verification, and every error-return path of
  every MCP tool.

A PR whose diff adds behaviour but no test that was red before it is not
reviewable. Say in the PR description which test drove the change and, where
it is not obvious, what the red output looked like.

## 2. Protected surfaces do not change outside a major release

Some strings and structures are load-bearing for verification that must
still work years from now. They are listed in [VERSIONING.md](VERSIONING.md):
the event schema and canonical serialization, the commit trailer keys, the
SPIFFE ID grammar, the MCP tool names and error-class vocabulary, and the
`innsegl` namespace.

If your change touches any of them — including a rename, a reordering, a
"harmless" spelling fix, or a new enum value — **stop and open an issue
first.** These change only in a major release, with a new `schema_version`
accepted alongside every previous one, updated golden fixtures, a signed
migration attestation, and a superseding ADR. CI diffs the golden fixtures
and contract schemas against the previous tag, so an accidental change fails
the build rather than shipping.

Flag any such change loudly in the PR description even when you believe it
is a no-op.

## Everything else

### Before you start

- Open an issue, or claim an existing one, before non-trivial work. Bug
  reports should include the root cause once known.
- Architectural decisions get an ADR under `docs/adr/` — the canonical
  serialization format, the idempotency store, the sealing cadence, and
  anything comparable. Write the ADR before the code.
- Suspected vulnerabilities do **not** go in issues. See
  [SECURITY.md](SECURITY.md).

### Building and testing

```bash
go build ./...
go vet ./...
go test ./... -race
golangci-lint run
go test ./... -coverprofile=cover.out && go tool cover -func=cover.out
```

Dashboard, from `web/`:

```bash
npx tsc --noEmit && npm run build && npm test
```

CI gates on the full suite green, the coverage floors, lint, and the
verification checks. A red CI run is not a review comment to argue with.

### Source file headers

Every source file carries an SPDX identifier as its first line, in the
comment syntax of the language:

```go
// SPDX-License-Identifier: Apache-2.0
```

CI checks this. A file without it fails the build.

### Commits and pull requests

- Conventional prefixes: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`.
  Scope where it helps — `feat(ledger): add hash chain append (#16)`.
- Reference the issue number in the commit subject.
- Keep a PR to one concern. A refactor and a behaviour change in one diff
  will be sent back to be split.
- Update `CHANGELOG.md` under `## [Unreleased]` for anything a user or
  operator would notice.

### Attribution rules — these are enforced

Innsegl exists to make attribution honest, so the project's own history has
to be honest too.

- **Never add a `Co-authored-by:` trailer that resolves to an account** that
  did not author the work. No commit may cause a GitHub contributor to be
  added for automated work.
- **No AI-attribution markers anywhere** — not in commit messages, not in
  code comments, not in documentation. No "generated by", no tool name, no
  assistant credit. Agent identity belongs in the `Agent-Identity`,
  `Agent-Run` and `Agent-Task` trailers and in the signature, and nowhere
  else.
- Commit author email must match the configured human or deliberately
  unlinked pattern. CI asserts this.
